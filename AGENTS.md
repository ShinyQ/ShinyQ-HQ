# AGENTS.md: conventions for ShinyQ HQ

Read this before changing anything. It applies to humans and AI agents in every build phase.

## Source of truth

- Design: `docs/superpowers/specs/2026-10-09-agent-hq-design.md` plus appendices `docs/superpowers/specs/agent-hq/01..08`. An appendix wins over the main spec for its topic.
- Owner content decisions C1 to C9 (appendix 07 section 7) override everything else about content.
- Phase plans live in `docs/superpowers/plans/`. Write one before starting a phase.

## Hard rules

- **No em dashes** (U+2014) anywhere: code, comments, copy, docs, commits, PR text. A unit test scans the repo. Use commas, colons, parentheses or "to".
- **Public repo.** Never commit private evidence, private repository names, cloud resource names, phone numbers, addresses, ID numbers, money amounts, salary or review text, the Master's degree, 2026 hackathon entries or any photo.
- **No client company names (C3, revised 2026-10-10).** Clients of the owner's employers (for example the bank, automotive, bakery, mining, lender and insurer clients) never appear on the site: not in text, alt text, slugs, metadata, OG cards, JSON-LD, search, room views or 3D labels. Use a sector label instead (`Pod.client` as `{ en, id }`, e.g. "National digital bank" / "Bank digital nasional"). Employers stay named (Metrodata / PT Mitra Integrasi Informatika, Jenius (SMBC Indonesia) for the 2024 to 2025 job only, Jatis, MNC, internships), and so do the freelance clients in C8. Product names are allowed, including MII / Metrodata products (ARIA, Pris.AI, MII Fraud Detection, MII E-Recruitment, eVendor, MII Deck, MII AI Ticketing; ATLAS and FREDDY are client work, so they get a sector label); never claim a product the owner did not build (Deck Studio inside MII Cowork, not all of Cowork). Sole exception: the owner's CV PDF in `public/cv/`, committed byte for byte at the owner's request (it may list items the site text hides); never edit or regenerate it. Its page images in `public/cv/pages/` (rendered by `bun run cv:pages` for the CV viewer) share that exception; never OCR them into site text or alt text (alt text is "CV page N of M").
- **Content is data.** Pages, rooms, pods and missions are generated from `content/site-content.json`. Never hardcode career facts in components.
- **Bilingual.** Every user-facing content string is `{ en, id }`. Indonesian is natural and professional ("saya"), technical terms stay in English. UI strings live in `messages/en.json` and `messages/id.json` with identical keys.
- **Static export.** `output: "export"`: no server runtime, no middleware/proxy, no API routes, no `next/image` optimization. Every route must pre-render through `generateStaticParams` and set `dynamicParams = false` on dynamic segments.
- **Every route works without WebGL.** 3D (Phase 1+) mounts client-side on top of the HTML pages and must never replace their content.

- CV: the owner's own PDF at `public/cv/{roof.cv.fileName}.pdf` (owner decision: use it as-is, English only, no web export). Owner decision: every CV entry point opens the in-site CV viewer modal instead of downloading. Use `<CvButton>` (`src/components/cv/CvButton.tsx`: a real link to `/{locale}/cv` that calls `openCv()`, so it works before hydration and with modifier keys) or `openCv()` from `src/hud/events.ts`. After adding or replacing a PDF run `bun run paper:pages` (refuses text that matches `PERSONAL_DATA_PATTERNS` or the blocklist; `tests/content/papers.test.ts` pins the sha256 and runs the same check when `pdftotext` exists). `buildPaperPreview` adds `PaperPreview.document` (`pdf`, `version`, `notice`, `pageCount`); page images stay out of the preview (the lazy reader reads `paperPages(file)` from `@/lib/papers`). ## Content style

- **Title Case for titles** (owner decision 2026-10-12): pod, post (`site-content.json` and the MDX frontmatter `title`), publication, talk, side project, award and principle titles are stored in Title Case in both locales, never cased with CSS `text-transform`. The rules live in `titleCase` (`src/content/title-case.ts`): capitalize every word except minor words that are not first, last or right after a colon (English: a, an, and, as, at, but, by, for, in, of, on, or, the, to, vs, via, with; Indonesian: dan, di, ke, dari, untuk, yang, dengan, atau, pada, plus the PUEBI prepositions dalam, bagi, oleh, serta, tentang, sebagai, terhadap, kepada; both lists apply in both locales because titles mix languages), keep words with an inner capital as written (AI, SaaS, PoC, IndoBERT), fix brands through `BRAND_CASING` (iOS, e2e, .NET; common words such as "it" or "line" are never in it), and case each part of a compound (E-Commerce, Chart-of-Accounts, Error-nya). Creative titles the author styled on purpose go in `TITLE_CASE_KEEP`.
- Not titles: role titles, org and certification names, skill group labels (rendered uppercase), mission labels (sentence-case actions) and body text.
- `tests/content/title-case.test.ts` and `bun run validate:content` fail on a title that `titleCase` would change; `bun scripts/title-case.ts` lists them and `bun scripts/title-case.ts --write` fixes `site-content.json` and the MDX frontmatter. A post's frontmatter title must equal its `site-content.json` title. Slugs and URLs never change with a title.
- **Gallery first** (owner decision 2026-10-12): every project list (Page View Work, Home, Quick view, Cmd-K, drawer prev/next, the L3 docking order, the wing boards and "Tour my projects") uses one order: `orderPods` / `comparePods` in `@/content/selectors` (pods with at least one gallery image first, then hero, featured, listed, then `order`). Never hard-code slugs to reorder; add a gallery or change `tier`/`order` in content. Topic questions in `content/ask/suggestions.json` that ask about one project follow the same order (`tests/ask/suggestions.test.ts`). The Ask "Projects summary" chunk keeps its own hero-first order on purpose: it answers "best project" questions.
- Mission labels that name a wing use the wing names from `common.wing` ("Product Engineering", "AI Engineering"); `tests/content/dataset.test.ts` checks `best-swe` and `best-ai`.

## Point-and-go (owner request, October 2026)

- The rover never drives to a clicked floor point. ## Public-safety lint

- `tests/content/safety.test.ts` scans `site-content.json`, MDX and messages with the merged blocklist (committed default + `content/.safety-blocklist.local.txt` + `SAFETY_BLOCKLIST` env var, which CI reads from a repository secret) and forbidden patterns (em dash, money, phone numbers, Azure hostnames, Master's degree).
- The committed default list names the client companies (C3); they are public companies, not secrets. SMBC Indonesia was also an employer, so its term is a regex that only allows the exact employer label "Jenius (SMBC Indonesia)". Add any new client of an employer there.
- `content/safety-allowlist.txt` lists the allowed product names; `loadBlocklist` drops matching terms from every source (a plain term equal to one, or a `/regex/` that names one), so an older private list never flags them. Never add a client name (a unit test checks).
- `e2e/deploy.spec.ts` runs `scanBuildOutput(out, loadBlocklist())` over every `.html`, `.txt`, `.json`, `.xml` and `.webmanifest` file of the export, so a client name cannot reach a page, RSC payload, sitemap or room data file.
- Blocklist format: one term per line or comma separated, `#` comments. Plain terms match case-insensitively on word boundaries; `/regex/` terms are case-sensitive.
- Validate content edits quickly with `bun run validate:content`.
- Live links (R4-J): the Azure hostname pattern stays forbidden in all copy, except a pod's `liveUrl` leaf whose URL passes `isPublicLiveUrl` (`leafForbiddenPatterns(leaf)` in `src/content/safety.ts`, used by the content test and `validate:content`). `loadBlocklist` also drops a private term equal to a public host or its App Service name (`PUBLIC_LIVE_NAMES`: `mii-microsoft`, `mii-microsoft-ai`), so a private list naming them cannot flag the public URLs; every other resource name stays private and blocked. They stay out of `content/safety-allowlist.txt` on purpose: that file also feeds the Ask entity allowlist, where `mii-microsoft` would let "worked at Microsoft" pass the employer check.

## Workflow

- Package manager: Bun. Scripts: `dev`, `build` (static export; `build:web` is an alias), `typecheck` (`next typegen && tsc`), `lint`, `test`, `verify:quick`, `e2e` (plain `playwright test`), `e2e:full`, `e2e:changed`, `e2e:smoke`, `e2e:shard`, `screenshots`, `screenshots:pages`, `serve`, `validate:content`, `floor:thumbs`.
- Before pushing: see "Fast verification" below (`verify:quick` plus `e2e:changed`); CI runs the full sharded suite.
- Commit in logical steps with conventional messages (`feat:`, `fix:`, `test:`, `docs:`, `ci:`, `chore:`). Prefer the `rtk` git wrapper. One PR per phase; do not merge without the owner.
- CI (`.github/workflows/ci.yml`) runs check and the build in parallel, e2e in 4 shards against that one build, the aggregate required check `Build, CV and e2e` (merged HTML report), a blocking `Lighthouse CI` job (`lighthouserc.json`: LCP 2 s, CLS 0.01, TBT 200 ms and transfer budgets for fonts, HTML, CSS and JS fail the aggregate check; see `docs/deploy.md` section 8 for what keeps LCP low), and a Cloudflare Pages preview (project `vars.CF_PREVIEW_PROJECT`, default `shinyq-hq`) only when `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` exist.
- Production (`.github/workflows/deploy.yml`) runs only on `workflow_dispatch`: by hand, or from `refresh-facts.yml` after it merges the weekly live-facts PR (`AUTO_DEPLOY_FACTS=false` stops that). A push to `main` never deploys. It builds, runs e2e, deploys `out/` plus `functions/`, smoke-checks production (`scripts/deploy-smoke.ts`) and opens a `deploy-failed` issue on failure. PR previews are off unless `CF_PREVIEWS=true`. Owner setup: `docs/deploy.md`.
- Build-time env: `NEXT_PUBLIC_SITE_URL` (canonical origin, default `https://kurniadi.pages.dev`, from `vars.SITE_URL`) and `NEXT_PUBLIC_CF_BEACON_TOKEN` (Cloudflare Web Analytics, omitted when unset; only production builds in `deploy.yml` set it, from `vars.CF_BEACON_TOKEN`).
- Audio: use `audio` / `useAudio` from `@/lib/audio`; never create another `AudioContext`. Sounds are synthesized, so there are no audio files to add. Sound is on by default (owner decision): a missing `hq:sound` means on, a stored `"off"` stays muted, and the context starts on the first user gesture. `Experience` calls `audio.setPaused(false/true)` on mount/unmount, so the Page View and static tier stay silent without changing the stored choice.

## Fast verification

The full local suite takes 20 to 40 minutes on SwiftShader; most of it covers code you did not touch. Verify what you changed locally and let CI run everything.

- Before every push: `bun run verify:quick` (typecheck, lint, unit tests, `next build`, about 1 to 2 minutes), then `bun run e2e:changed` (only the specs that cover your changed paths, usually 1 to 4 minutes). Together about 5 minutes.
- `e2e:changed` diffs against the merge base with `origin/main` plus staged, unstaged and untracked files and maps paths to specs in `scripts/e2e-plan.ts` (for example `src/experience/floors/labs/**` to `labs`, `gallery` and `walk`, `src/experience/interact/**` to `interact`, `experience`, `pads` and `career`, `src/app/**` and `src/components/**` to `pageview`, `static-routes` and `gallery`, `src/hud/drawer/**` to the drawer specs, `drawer-solid` included, `src/hud/dialog/**` and `src/experience/hints/**` to `onboarding`, `experience` and `walk`). Changes to `e2e/hq.ts`, `playwright.config.ts`, `package.json`, `bun.lock` or `next.config.ts` run the full suite; unmapped paths add the smoke specs; docs and unit tests run nothing. `--dry` prints the plan, `--base <ref>` changes the base, extra args go to Playwright (`bun run e2e:changed --headed`). When you add a spec or a folder, add its rule (a unit test checks every spec is known).
- `bun run e2e:smoke` (static routes, SEO, deploy rules, game-first load, Page View, about 1 to 2 minutes) is the fallback when unsure. `bun run e2e:full` (whole suite, about 6 to 10 minutes locally) only when you change shared test infrastructure, before a phase PR, or to reproduce a CI failure locally (`bun run e2e:full e2e/career.spec.ts -g "swipe"`).
- Screenshots (`bun run screenshots`, `screenshots:pages`, 15 minutes or more) run only when visuals change and the owner asks for captures, or in CI: nightly on `main`, on demand (Actions > Screenshots > Run workflow) or on a PR labelled `screenshots` (also automatic for changes under `docs/design/**`). Artifacts: `screenshots`.
- Workers: Playwright uses 2 workers locally and on each CI shard (4 vCPU runners). Every worker renders WebGL on the CPU, so more workers starve each other and make 3D tests time out; do not raise it. Do not run two e2e suites at once on one machine.
- Turbopack can serve stale CSS after large style or dependency changes: `rm -rf .next` before `verify:quick` if the export looks wrong. `e2e:*` serves `out/` from the last build, so rebuild after code changes (`verify:quick` does).
- Writing 3D tests: wait on state, never on time. Use the helpers in `e2e/hq.ts`: `enterHQ`, `enterFloorRoute` (deep link, waits for the scene loop), `waitForSceneLive` (the phase is `explore` before the first frame on deep links, and input sent earlier is dropped), `waitForCameraSettle` (counts rendered frames, so a stalled main thread does not look settled), `waitForFrames`, `waitForFloor`, `waitForRoom`, `waitForRoverMove`, and `expect.poll` for values. On static pages, `openPage(page, url)` (or `waitForHydration` after a reload or full navigation) before clicking client islands: the Next.js chunks load after first paint, so `load` fires before hydration (signal: `html[data-hydrated]`, set by `MissionHud`). `page.waitForTimeout` is only for proving that nothing happens (for example that `?tier=static` never mounts the canvas). Pass `?tier=lite` (no bloom or motes) unless the test is about the full tier. No blanket retries: CI retries once; fix a flaky test instead of adding retries.
- CI shards with `scripts/e2e-shard.ts` (round-robin over `playwright test --list`, so every shard gets part of every slow 3D spec; Playwright's own `--shard` cuts contiguous blocks). Shards upload blob reports that `Build, CV and e2e` merges into the `playwright-report` artifact. To reproduce a shard locally: `bun run e2e:shard 2/4`.
