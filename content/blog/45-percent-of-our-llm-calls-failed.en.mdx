Early in building an AI CV screening platform at Metrodata, I ran a batch of 22 candidate and job pairs through the pipeline (2 job posts by 11 candidates). About 45% of the screening evaluations failed. Not low scores: no usable result at all.

This post covers the fix and, just as important, what the fix did and did not prove. The short version: I stopped guessing, read the two error strings the pipeline actually produced, mapped each one to a root cause, fixed both in layers, and turned those exact strings into regression tests.

## The setup

The platform helps recruiters screen CVs. A recruiter defines a job post, the system extracts a weighted requirement rubric, and an LLM evaluates every candidate against that job and returns structured JSON: a fit score, evidence and a written rationale. Today a human recruiter makes the decision and the AI supplies evidence.

Each evaluation ran as an Azure Durable Functions activity calling a reasoning model on Azure AI Foundry through the Responses API. The original parsing path was simple: strip any markdown code fences from the reply, then call `json.loads`. When that worked, everything downstream worked. When it did not, the pair was lost.

## Two strings instead of one vague problem

"The LLM sometimes returns bad JSON" leads to random prompt tweaks. Instead, I grouped the failures by error message. There were two:

- `Response missing required keys: {'fitScore'}`
- `Invalid control character at: line 15 column 95`

Two strings usually mean two mechanisms.

## String one: the answer ran out of room

The first clue was which key was missing. `fitScore` was the last key in the output schema. If a model dropped fields at random, random keys would go missing. When it is the final key, the more likely explanation (reasoning, not a measurement) is that the output stopped before the model got there.

The configuration explained why. Reasoning effort was set to high, the prompt asked for a long written rationale (10 to 15 sentences), and there was no explicit output token ceiling. On a reasoning model, the hidden reasoning tokens and the visible answer draw from the same output budget. Long reasoning plus a long rationale exhausted the budget mid-JSON, and the last field never arrived.

The prompt had a smaller problem too: it told the model not to use code fences, then showed a fenced example. Contradictory instructions are cheap to fix.

## String two: a newline where JSON forbids it

The second string is the message Python's `json` module raises in strict mode when a string value contains a raw control character. The cause: the model had written literal newlines inside JSON string values instead of the escaped form. Close to valid JSON is still invalid JSON.

## The layered fix

No single change covered both causes, so I fixed them in layers:

1. **JSON mode.** I set `response_format` to `json_object` so the API constrains the reply to JSON instead of relying on the prompt alone.
2. **Output token ceilings.** Explicit limits of 6,000 and 16,000 tokens for the two call types, so the budget is a deliberate decision rather than an accident.
3. **Lower reasoning effort.** High to medium, so less of the budget goes to hidden reasoning before the answer starts.
4. **A quote-aware JSON extractor.** Instead of stripping fences with a pattern, the extractor finds the JSON object by balancing braces while tracking whether it is inside a string, so a brace inside a quoted value does not end the object early.
5. **Control-character escaping inside strings only.** Raw newlines and tabs are escaped when they appear inside a string value, and left alone between tokens, where they are legal whitespace.
6. **Retries that keep the books straight.** Up to three attempts per call, with token usage summed across attempts so retries still show up in usage accounting. After the third failure the error is re-raised, so the Durable Functions retry policy can take over.
7. **Prompt fixes.** No more fenced example under a "no fences" rule.

Here is a generic sketch of layer 5. It is illustrative, not the production code:

```python
ESC = {"\n": "\\n", "\r": "\\r", "\t": "\\t"}

def escape_controls(raw: str) -> str:
    out, in_str, esc = [], False, False
    for ch in raw:
        if esc:
            esc = False
        elif in_str and ch == "\\":
            esc = True
        elif ch == '"':
            in_str = not in_str
        elif in_str and ord(ch) < 0x20:
            ch = ESC.get(ch, f"\\u{ord(ch):04x}")
        out.append(ch)
    return "".join(out)
```

The `in_str` flag is the point. A blanket newline replace would also rewrite valid whitespace between keys; tracking quotes and escapes keeps the change surgical.

## Turning the failures into tests

The fix shipped with 7 unit tests that reproduce the exact failure strings from that run, fed through the new parsing path. All 7 passed, and so did the rest of the core test suite (12 of 12) at the time. The platform had only started getting tests a few days earlier, so these were among its first.

A synthetic "malformed JSON" fixture tests what you imagine can go wrong. A fixture built from what the model actually returned tests what did go wrong, and it fails loudly if someone later "simplifies" the parser back to `json.loads`.

## What I can and cannot claim

This is the part I want to be careful about.

**What is verified:** about 45% of evaluations failed in that 22-pair run; the two error strings above; the root causes; the layered fix; the 7 regression tests passing.

**What was not recorded:** I did not record a rerun of the same 22 pairs after the fix. So I cannot give you a "45% to X%" number for that run, and I will not invent one. What I can say is that the two failure mechanisms are identified, fixed, and covered by tests.

**A separate, later number:** months later the project had an offline evaluation harness. Its baseline measured a final parse failure rate (after retries) of 0.13%: 1 of 800 non-adversarial calls. That run used a newer model and a different prompt version, so it is not a before-and-after measurement of this fix. It shows where reliability stood at that later baseline, not what this specific change achieved on its own.

## Related findings

Three later problems on the platform rhymed with this one:

- **Retries that did not retry.** The Durable Functions retry I relied on in layer 6 was not reliably firing, and outcome counters could double count. The fix was a single retryable versus terminal classification, plus writing the outcome marker and the counter in one transactional batch.
- **Evals measuring the wrong thing.** Throttling (HTTP 429) responses were being counted as schema failures, and one eval run measured an older code revision. Transport failures are now counted separately, and every run records a fingerprint of the code under test.
- **Silent stalls.** About 3% of model calls stalled until the SDK's default 600 s timeout. Explicit per-call deadlines (90 s for screening, 240 s for deep analysis) now bound every call.

Reasoning effort also came back later as a latency question. In controlled evaluation rounds, screening p95 latency was 21.1 s at high effort and 12.1 s at medium, with the fairness and prompt-injection gates still passing at medium. Medium shipped.

## Lessons for structured-output reliability

- **Read the error string before changing anything.** Two strings meant two mechanisms. Grouping failures by message turned a scary percentage into two concrete bugs.
- **Which field is missing is a clue.** A consistently missing last key points to truncation, not to a model that "forgets".
- **Reasoning tokens share the output budget.** Set an explicit ceiling, and treat reasoning effort as a budget knob, not only a quality knob.
- **Use the API's JSON mode, then still parse defensively.** Constraints reduce failures; a quote-aware extractor and bounded retries handle the rest.
- **Keep retries honest.** Sum tokens across attempts, cap the attempts, and re-raise so the next layer can decide.
- **Save the real failures as tests.** They are the cheapest insurance against someone undoing the fix.
- **Say what you did not measure.** A fix with a clear root cause and regression tests is a solid claim. A post-fix number you never recorded is not.
